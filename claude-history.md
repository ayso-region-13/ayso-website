## Retired gotcha — CF Pages blob-hash poisoning (MOOT since 2026-06-18)

This was a symptom of CF's **Git-integration** build pipeline, which we **retired** — both projects now deploy via CI `wrangler pages deploy` (Direct Upload), so the `initialize`/`deploy`-stage failures that caused poisoning no longer occur and wrangler re-uploads deterministically. Kept for history / the rare manual case:

When a Git-pipeline Pages deploy failed at `stage=initialize` or `stage=deploy`, the uploaded bytes could end up as a poisoned blob in CF's content-addressed storage. Subsequent deploys reported success but still served `HTTP 500` with empty body on every URL whose content matched the poisoned hash. Fix: mutate the affected file bytes to force a new hash. **PDFs / binaries**: `printf '\n' >> file.pdf` is enough (readers tolerate trailing junk past `%%EOF`). **HTML pages**: a trailing newline in the `.md` source is NOT enough (markdown-it strips it; rendered HTML is byte-identical) — inject something that survives rendering, e.g. `<!-- vN hash-bust -->`. Confirm by hitting the deployment-specific URL `https://<deployId>.ayso-website-staging.pages.dev/<path>` — if it 500s there too, it's poisoning, not CDN cache. See commits 613da27 + 5d1365c (2026-05-22) for the worked example.
