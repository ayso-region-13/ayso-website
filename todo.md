- [ ] **The csp-report admin endpoint returns the OLDEST reports, not the recent ones (found 2026-08-31, session 51).** `GET /api/csp-report?admin_key=…&limit=N` is documented as "Recent reports", and it silently stopped being that once the namespace outgrew `MAX_LIST_LIMIT`. Keys are `${ISO-timestamp}-${id}`, so KV lists them **ascending**; `workers/csp-report/src/index.js:101-102` calls `list({ limit })` and then sorts/reverses **only the page it already fetched**. The namespace currently holds **9,899 keys** against a 1000 cap, so even `limit=1000` returns Aug 1-7 data. This is actively misleading rather than merely limited: a query looks authoritative and returns a confident answer about four-week-old traffic. It nearly produced a false "no PostHog violations" verdict during the session-51 promote check.
  **Fix options, cheapest first:** (a) paginate with the `cursor` from `list()` and keep only the last N — correct, and `list_complete` already tells you when to stop; (b) list with a `prefix` derived from the last day or two, which is what the manual workaround does; (c) reverse the key so it sorts descending (`${9999999999999 - epochMs}-${id}`), which makes the current single-page code correct but does not migrate existing keys. Option (a) is the honest one.
  **Manual workaround until then:** `npx wrangler kv key list --namespace-id=d6a804159968475db6bcbf7354b45d0f --prefix="$(date -u +%Y-%m-%d)" --remote` from `workers/csp-report/`, then `wrangler kv key get` the ones you want. `--remote` is not optional; without it you read an empty local store, and a local miss looks exactly like "no violations".
  **While you are in there:** volume is ~500 reports/day (867 on 2026-08-27), essentially all `stats.g.doubleclick.net` from GA4 Google Signals, which is already known not to be ours. The 30-day TTL is not keeping this small, and the noise is what makes a real violation easy to miss.
